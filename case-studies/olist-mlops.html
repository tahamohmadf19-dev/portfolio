MLOps and model serving

Educational prototype

Olist MLOps

Predict whether an Olist e-commerce order will arrive late, and serve that prediction through a tested, monitored API instead of a notebook.

Status
Educational project, not deployed. The model is weak: test ROC-AUC 0.61 at a 4.28% late rate.
Source
Read the code
Stack
Python, scikit-learn, FastAPI, Docker, Prometheus, DVC, MLflow, GitHub Actions

My role

My project in an MLOps training course. The model-evaluation write-up and the Kaggle reproduction were added in November 2026 with an AI coding agent.

How it works

This diagram follows the real path through the code. Select a stage to read what happens there. Stages marked with a diamond are control points, where the system checks, stops or waits for a person.

Engineering decisions

  • Reported the weak test result (ROC-AUC 0.61, accuracy below an always-on-time baseline at the chosen threshold) instead of accuracy alone.
  • Chose the threshold on validation only and used the later test period once.
  • Documented the point-in-time leakage risk of historical aggregates instead of claiming real-time readiness.
  • Kept data and model files out of Git, tracked by DVC pointers, and stated that a fresh clone cannot serve predictions.

What was tested

  • 172 tests in GitHub Actions (run 42863988828), reproduced from a fresh clone on 2026-11-14.
  • Kaggle re-run from raw data: test PR-AUC 0.06704 and ROC-AUC 0.6115, matching the saved bundle.
  • Validation ROC-AUC 0.746 and PR-AUC 0.125; test ROC-AUC 0.611 and PR-AUC 0.067 at a 4.28% late rate.

Limits and open work

  • Not verified for purchase-time inference: some aggregates may include later updates.
  • No DVC remote or published model, so a fresh clone runs the tests but cannot serve predictions.
  • No alert notification channel and no store joining predictions with outcomes.
  • The model's predictive value is weak; the project's value is the inference engineering.
